The agent bridge with the real tools, on the maintainer's lab accounts, with the maintainer's permission of 2026-10-25 ("launch limited 1 or 2 desktop or CLI actual tools for testing", "in a throwaway lab folder"). Run by claude-opus. Real names, emails, account ids and local paths are left out; `<claude-profile>` is the Claude Code config folder used, `<lab>` the throwaway git repo (a README and a three-line shell script), `<data>` a fresh AI Juggler Dev data folder.

## How it ran

- **Through AI Juggler's own launch code, not by clicking in the window.** No desktop control was available to this run. The read-only test bridge (`docs/qa/DEV-BRIDGE.md`) can't launch. So a lab harness, an ignored and env-gated test in the shape of `switch_lab_live.rs`, built an `AppState` over `<data>`, brought both accounts in **in place**, answered the one-time question yes, inserted a running session row, asked each adapter for its `LaunchMode::Headless` spec, and called `agent_bridge::prepare` exactly as every launch path does. It then ran the spec's own program, arguments and environment.
- The harness was not committed (lab only; kept in the session scratchpad).
- **Headless, not the TUI.** `claude -p` and `codex exec` show no interactive prompt. An approval they would need appears as a refusal in their output instead (`permission_denials` for Claude, a failed tool call for Codex). That makes a "needs approval" case visible in the output, and the Codex control below shows it.
- A new folder in the interactive TUI would also first ask "trust this folder?". The lab rules say to stop at any permission question, so the TUI's own screens were not exercised.
- **The bridge program.** It was the real `juggler-agent` (debug build) behind a three-line wrapper that copies the MCP lines both ways to a log, to read the protocol version (stdin and stdout only, never the environment). The wrapper had to live outside `/tmp`: `program()` refuses a program in a folder others can write (`file_trust::trusted_executable`). That is correct behaviour, seen live.
- **Order.** Claude first, then Codex, in the same `AppState`, so the second could see the first in `pool_roster`. One real tool process ran at a time.

## A bug found on the way

`ClaudeCodeAdapter::launch_spec` with `LaunchMode::Headless` gives `-p <prompt> --output-format stream-json` without `--verbose`. Claude Code 2.1.302 refuses that at once: `Error: When using --print, --output-format=stream-json requires --verbose` (exit 1, about 2 s, no model call). With `--verbose` added at the end, the same launch worked. The bridge isn't involved. Any headless Claude launch through the adapter fails until this is fixed (`crates/juggler-adapters/src/claude_code.rs`, the `Headless` arm).
