Drawing the Floor: a webview canvas or a native window

Two minimal spikes draw the same office from the same data. The office has 8 App zones, 150 desks and 142 people, 40 of whom move: 33 typing, 6 walking and one waving with a bubble, plus a small desk fire. A fixed camera looks onto a back wall with windows and doors and a glass side wall, drawn at 852×532 and scaled up with hard edges. Each spike draws only when something changes, in a window that pops out beside a minimal Tauri main window, as AI Juggler's would. Measured on this Mac on 2026-11-03 09:33, then checked on GitHub's Windows and Linux runners.

Recommendation: option 3, the native wgpu window, if the Floor is to animate all day; with three conditions

  • Why. On this Mac the native window costs about a quarter of the Canvas window's CPU and energy at every frame rate:
    • 0.8 vs 3.1 % of a core at 6 fps;
    • 1.0 vs 4.1 % at 10 fps;
    • 2.4 vs 11.0 % at 30 fps;
    • 1.3 vs 4.6 % over ten minutes.
    Slowing the Canvas down doesn't close that gap: even at 6 fps it sits at about the old budget of 3 points of a core while animating. The native window also shows its first frame sooner and adds no process. At rest, covered and minimised, both cost close to nothing.
  • What it costs instead.
    • About 190 MB more graphics memory while animating: about 620 MB in all against about 430 MB. Both carry a fixed charge macOS makes for a presenting GPU layer, and it isn't explained yet.
    • 4.2 MB more binary and about 12 s more build.
    • More code: per-OS input and visibility (Tauri gives a window without a webview no mouse, keyboard or occlusion events), a text renderer, and accessibility outside the canvas.
  • Condition 1: close the gaps cheaply. Prove in the next step that input and visibility on macOS and Windows, plus text and menus, work. The leading idea is a transparent child webview over the native surface. If that proves fragile, fall back to option 1 with a frame cap.
  • Condition 2: a rule for machines without a GPU. On Windows without one, wgpu's software adapter pegged four cores in two of three runs. Detect a software adapter and drop to 1–2 fps, or to the Canvas path.
  • Condition 3: animate on attention. Animate only while the Floor is visible and was looked at recently. That also releases the fixed graphics memory both options hold while animating.

If engineering time matters more than CPU and energy, option 1 is the safe choice: it is simpler, accessible, and identical everywhere. It costs about 3–4 % of a core while people move on this Mac, and much more in software on Windows.

01 · the two spikes

The same scene, drawn two ways

Both draw from one Rust scene generator (projection, rasteriser, sprite atlas). Their frames match pixel for pixel apart from where the animation is in its cycle. Each window has a way back: the Canvas window has a button and a right-click menu, the native window an app-menu item, "Open Sessions in the main window" (⌘⇧S). Both call the same command, which brings the main window forward on that screen. I couldn't click the native menu from here (no UI automation on this Mac), so try it with the command in §05.

Where the time goes

  • Canvas: our drawing is about 0.2 ms a frame. Most of the cost is WebKit compositing the canvas across three processes (the app, WebContent and the WebKit GPU process) on every frame.
  • Native: about 0.35 ms a frame including present, all in the app's render thread.
  • GPU utilisation (ioreg, whole machine) stayed at idle level for both, about 9 %. The scene is trivial for this GPU.

Memory: a fixed graphics charge in both

  • While a window keeps presenting frames, macOS charges a block of GPU memory that footprint lists as "Owned physical footprint (unmapped) (graphics)": about 292 MB in WebKit's GPU process for the Canvas, and about 502 MB in the app for native.
  • It is not our textures, which total about 4 MB. It's the same at 1278×798 and at 640×400 (native 571 vs 565 MB; WebKit GPU 317 vs 317 MB).
  • It didn't shrink when the native surface was cut to the art's size, or when finished GPU work was freed every frame.
  • It goes away at rest, when covered and when minimised.
  • Over 10 minutes at 10 fps: Canvas 428 → 431 → 453 MB, native 620 → 586 → 586 MB (at 1, 5 and 10 minutes). Neither leaks.

Covered and minimised

  • Canvas: WebKit marks the page hidden and our ticker stops.
  • Native: it asks AppKit twice a second whether the window can be seen, and stops drawing when it can't. It still used about 1 % of a core while covered, in the app process, and that residual isn't explained yet.
  • Partly covered counts as visible, for macOS and for both spikes. That is the right behaviour.

Start-up, size, build

  • First frame after asking for the window: Canvas 330, 369, 425, 455, 463 ms; native 94, 128, 132, 162, 226 ms.
  • Release binary: 11.7 MB with the Canvas window only. wgpu adds 4.2 MB (15.9 MB).
  • Clean release build on this Mac (4 jobs, low priority): 63 s with the Canvas window only, 75 s with wgpu. wgpu adds about 12 s, or 52 s of CPU time.
  • Processes: Canvas runs WebKit GPU, WebKit Networking, WebKit WebContent, floor-spike; native runs WebKit GPU, WebKit Networking, WebKit WebContent, floor-spike. The native window adds no process; the main window's own WebKit processes stay in both.

  • Both options build, open, draw at the asked frame rate and quit cleanly on both systems.

04 · what it would take to build

Beyond the numbers

Canvas comes with

  • Text, hover, tooltips, context menus and focus.
  • The accessible list view, and the same React and Tauri stack as the rest of AI Juggler.
  • Visibility handling: WebKit and WebView2 hide the page when it is minimised or covered.
  • The round trip to the main window is one command.
  • Risk: each animated frame goes through the browser's compositor in other processes. That made it 4× the native CPU here, and very expensive in software on Windows.

native needs, on top

  • Input and visibility. Tauri 2.12 passes no mouse, keyboard or occlusion events to a window without a webview (WindowEvent has none). Clicks, hover and "am I covered?" need code per OS: AppKit on macOS, Win32 on Windows, GTK on Linux. The spike polls AppKit for visibility.
  • Text. Labels and bubble words need a text renderer such as glyphon or cosmic-text, which adds more megabytes and build time. Neither spike draws text.
  • Accessibility. There's nothing for screen readers unless AccessKit is wired in, so the list view would live in the main window.
  • Menus work through Tauri's menu: the spike's "Open Sessions in the main window" proves the round trip.
  • One way to close the gaps: a transparent child webview over the native surface for text, input and menus. It would redraw only when labels change, while the pixels animate in wgpu. That isn't tried yet; Tauri's multi-webview API is still marked unstable.
05 · how to check it

Run it yourself

The source is on the proto/floor-office branch in spikes/floor-spike, with its own workspace; it never joins the app's build. Each command opens a window and quits by itself.

cd spikes/floor-spike
nice -n 10 cargo build --release -j 4
./target/release/floor-spike --open web --anim 10 --exit-after 30      # option 1
./target/release/floor-spike --open native --anim 10 --exit-after 30   # option 3; menu: Floor ▸ Open Sessions (⌘⇧S)
python3 measure/run.py > measure/out/results-mac.json                  # the full measurement, about 27 minutes

Switches:

  • --anim 0|10|30: frames per second while people animate (0: nothing moves);
  • --cover-after S and --minimize-after S;
  • --size WxH;
  • --art-surface (native only: draw at art size and let macOS scale up);
  • --capture DIR.
